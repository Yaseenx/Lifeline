# Green-Corridor Backend — Standards-Based Requirements & Case Catalog

Every requirement, operational case, and failure mode a multi-junction emergency-vehicle green-corridor **backend** must handle to be deployable, drawn from real-world standards and fielded systems. Each item is tagged with the backend component it governs and a criticality flag, and is backed by a cited source.

**Component tags:** `[ARB]` arbiter · `[FSM]` per-junction state machine · `[CO]` corridor coordinator · `[MON]` safety/conflict-monitor · `[SEC]` security
**Criticality:** **CRITICAL** (safety/deployability — must implement) · **RECOMMENDED** · **OPTIONAL**

The single most important framing from the research: an ambulance green corridor is **preemption-class**, not priority-class. NTCIP 1211/1202 define *preemption* as transferring control to a special mode that **terminates normal control** (used for railroad, emergency vehicle, transit passage), whereas *priority* is preferential treatment **without dropping coordination**. So the corridor legitimately drops coordination and needs a **managed recovery** — but it inherits every hard safety constraint of preemption (clearance intervals, conflict monitoring, min-green). ([FHWA Signal Timing Manual Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [NTCIP 1211 v02](https://www.ntcip.org/file/2018/11/NTCIP1211-v0224j.pdf))

## 1. Arbiter — who gets the junction

- **ARB-1 `[ARB]` CRITICAL — Fixed priority order by class.** Serve in decreasing importance: **railroad > marine/drawbridge > heavy emergency (fire/EMS) > light emergency (police) > light-rail > bus/transit**. Railroad preemption is always highest within a controller. Rank "by importance of right-of-way and/or difficulty in stopping the class of vehicle." ([FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [Wikipedia: Traffic signal preemption](https://en.wikipedia.org/wiki/Traffic_signal_preemption))
- **ARB-2 `[ARB]` CRITICAL — Emergency preemption always overrides transit priority.** On a shared network "EVP always takes precedence when both are active"; commercial phase selectors make a high-priority input override any low-priority activation. ([Miovision EVP deployment](https://miovision.com/evp-deployment/); [Opticom GPS equipment spec](http://www.signalcontrol.com/products/gtt/Opticom_GPS_Intersection_Equipment.pdf))
- **ARB-3 `[ARB]` CRITICAL — First-come-first-served *within* a class; earlier SOS wins.** Rank by class first, then by request timestamp, then a stable tie-break (vehicle id). This is exactly how Opticom/EMTRAC resolve same-level requests. ([Opticom GPS spec](http://www.signalcontrol.com/products/gtt/Opticom_GPS_Intersection_Equipment.pdf); [EMTRAC EVP](https://www.emtracsystems.com/wp-content/uploads/2021/02/EMTRAC-EmergencyVehiclePreemption.pdf))
- **ARB-4 `[ARB]` CRITICAL — Serve one preempt at a time; queue the rest; a higher preempt overrides an active lower one.** ([FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [Wikipedia](https://en.wikipedia.org/wiki/Traffic_signal_preemption))
- **ARB-5 `[ARB]` CRITICAL — Controller/edge retains final authority.** NTCIP 1211: a priority request may be *sent* but "a CO cannot be **commanded** to service a priority request." The arbiter proposes; the junction's own safety logic disposes. ([NTCIP 1211 v02 §2.3](https://www.ntcip.org/file/2018/11/NTCIP1211-v0224j.pdf))
- **ARB-6 `[ARB]` RECOMMENDED — Reservice throttle / anti-thrash.** NTCIP 1211 defines a *Reservice Period* limiting how often a request is serviced, plus a `prsBusy` state. Rate-limit repeat requests from the same vehicle. ([NTCIP 1211 v02 §2.5/§4.2.5](https://www.ntcip.org/file/2018/11/NTCIP1211-v0224j.pdf))
- **ARB-7 `[ARB]` RECOMMENDED — Class + role come from an authenticated identity, never a self-asserted field.** SAE J2735 `RequestorType.role`/`RequestImportanceLevel` set precedence, so they must be bound to the vehicle's certificate/registry, not attacker-settable (see SEC-2). ([ISO/SAE J2735 ASN.1 module](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn))
- **ARB-8 `[ARB]` CRITICAL — Bound the request queue against flooding.** A peer-reviewed "congestion attack" shows high-rate specious/inauthentic requests starve legitimate ambulances; cap per-source and per-junction queue depth. ([ACM TCPS: Alleviating Congestion Attacks](https://dl.acm.org/doi/10.1145/3801748))

## 2. Per-junction state machine — how a junction changes safely

- **FSM-1 `[FSM]` CRITICAL — Yellow + all-red clearance may never be shortened or omitted, entering, during, or exiting preemption.** MUTCD §4D.27: "The yellow change interval, and any red clearance interval that follows, shall not be shortened or omitted." No instant flip to a conflicting green — ever. ([MUTCD 2009 §4D.27](https://mutcd.fhwa.dot.gov/htm/2009/part4/part4d.htm))
- **FSM-2 `[FSM]` CRITICAL — No steady-yellow → steady-green transition on exit.** Must pass through red. ([MUTCD 2009 §4D.27](https://mutcd.fhwa.dot.gov/htm/2009/part4/part4d.htm))
- **FSM-3 `[FSM]` CRITICAL — Clearance is enforced even when a preempt arrives during flash.** Program a full yellow+red when preempting out of MUTCD/local flash. ([MCDOT NEMA TS2 spec](https://atms.montgomerycountymd.gov/specs/ts2spec.htm))
- **FSM-4 `[FSM]` CRITICAL — Minimum green is protected before any switch.** Preemption "will ensure a programmed minimum green, pedestrian walk and pedestrian clearance time is met prior to terminating the phase." ([TxDOT Preemption](https://www.txdot.gov/manuals/rrd/rho/exhibit_a_and_pse_design/traffic_signal_preemption-i1005274.html))
- **FSM-5 `[FSM]` CRITICAL — Pedestrian clearance floor = crossing distance ÷ 3.5 ft/s + ≥2 s buffer; only truncate under genuine preemption where geometry forces it, never for routine corridor priority.** (MUTCD permits truncating ped intervals *into* preemption, but FHWA warns to allow "as much time as possible.") ([MUTCD 2009 §4D.27](https://mutcd.fhwa.dot.gov/htm/2009/part4/part4d.htm); [FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [CDOT Ped Signal Timing](https://www.codot.gov/safety/traffic-safety/assets/documents/guidelines-for-pedestrian-signal-timing-v2.pdf))
- **FSM-6 `[FSM]` CRITICAL — Do not cut a phase to yellow while high-speed vehicles are in the dilemma zone; hold green until clear, then run full clearance.** ([MUTCD 2009 §4D.04](https://mutcd.fhwa.dot.gov/htm/2009/part4/part4d.htm); [Urbanik, The Dilemma with Dilemma Zones](https://redlightrobber.com/red/links_pdf/The-Dilemma-with-Dilemma-Zones.pdf))
- **FSM-7 `[FSM]` CRITICAL — Canonical preempt sequence:** right-of-way transfer (entrance) → [track clearance, if rail] → dwell/limited-cycle (respect a **minimum dwell duration**) → exit/recovery. Model these as explicit states. ([TxDOT Preemption](https://www.txdot.gov/manuals/rrd/rho/exhibit_a_and_pse_design/traffic_signal_preemption-i1005274.html); [Sebago: Basics of a Preemption Event](https://www.sebagotechnics.com/wp-content/uploads/Preemption.pdf))
- **FSM-8 `[FSM]` CRITICAL — Every hold is time-bounded and auto-reverts.** J2735 request carries an ETA + **duration**; "if the vehicle does not clear … when the duration is reached, the request will be cancelled and the intersection will revert to normal operation." A green-hold must never be open-ended. ([ISO/SAE J2735 ASN.1](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn); [Princeton CITP: default-to-old-behavior](https://blog.citp.princeton.edu/2003/10/27/remote-controls-traffic-lights/))
- **FSM-9 `[FSM]` RECOMMENDED — Distinguish the three junction actions:** *call/switch to green*, *extend/hold green* (needs no extra clearance), *early-green/red-truncation*. TSP toolkit; each has different clearance implications. ([FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [Applied Information Glance](https://appinfoinc.com/solutions/glance-travelsafely/))
- **FSM-10 `[FSM]` CRITICAL — Auto-release on pass/park.** Opticom units deactivate on shift-to-Park and clear when the vehicle passes; a signal is "never locked down and held green indefinitely." ([Galax FD: Opticom](https://galaxfire.com/equipment/opticom/))

## 3. Corridor coordinator — the green wave across 3 junctions

- **CO-1 `[CO]` RECOMMENDED — Offset = inter-signal distance ÷ progression speed;** subtract queue-clearance time so the wave runs slightly ahead of the platoon. This is the core green-wave math for arming J1→J2→J3. ([Wikipedia: Green wave](https://en.wikipedia.org/wiki/Green_wave); [FHWA Ch.6](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter6.htm))
- **CO-2 `[CO]` RECOMMENDED — Arm the *next* junction by ETA/distance look-ahead**, tuned per vehicle class; emergency vehicles are detected farther out (~500 m) than buses "to allow a smooth and safe transition to green." ([Leeds UTMC01 review](https://www.its.leeds.ac.uk/projects/spruce/utmc1rev.html); [Opticom GPS spec — ETA/distance range](http://www.signalcontrol.com/products/gtt/Opticom_GPS_Intersection_Equipment.pdf))
- **CO-3 `[CO]` CRITICAL — Share preemption status with adjacent junctions.** ARC-IT: roadway equipment "shall report current preemption status to other field elements at adjacent intersections." This is the coordinator's job. ([ARC-IT Roadway Signal Preemption](https://www.arc-it.net/html/functionalobjects/funobj368.html))
- **CO-4 `[CO]` CRITICAL — Expect and manage a multi-cycle recovery, not an instant snap-back.** Field-measured recovery to base coordination ran **30 s to 7 minutes**; pick a transition method (short/long/add/subtract/dwell) — "shortway" is least effective. ([FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [Transition-strategy study](https://vtechworks.lib.vt.edu/items/b18b1b83-bfe0-4e2e-a0cb-fac56bcb78b0))
- **CO-5 `[CO]` CRITICAL — Don't discharge a green into a full box.** Model downstream storage; queues can spill back into an adjacent junction and blockage defeats the corridor — interconnect and check storage before granting. ([NCHRP Synthesis 507](https://transops.s3.amazonaws.com/uploaded_files/NCHRP%20Synthesis%20507%20Traffic%20Signal%20Preemption%20at%20Intersections%20Near%20Highway%E2%80%93Rail%20Grade%20Crossings.pdf))
- **CO-6 `[CO]` RECOMMENDED — Rolling hand-off:** release each junction as the vehicle clears it, rather than holding the whole corridor green. Matches the Opticom "steady-on-granted-approach, resume-on-pass" model and the KPI that bandwidth efficiency ≈ 40–55%. ([Green wave / bandwidth](https://en.wikipedia.org/wiki/Green_wave))
- **CO-7 `[CO]` OPTIONAL — Reverse/negative offset** to clear a downstream queue first when spacing/speed warrant. ([Green wave](https://en.wikipedia.org/wiki/Green_wave))

## 4. Safety / conflict monitor — the independent last line

Model this as a **separate process** the corridor logic cannot override; on any fault it forces flash-red/all-red and **latches until explicit reset**. This mirrors the NEMA TS2 MMU/CMU and the EN 12675 functional-safety requirement that conflicting vehicular/pedestrian movements be controlled safely. ([EN 12675](https://standards.globalspec.com/std/10257398/EN%2012675); [EDI MMU2-16LE manual](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))

- **MON-1 `[MON]` CRITICAL — Conflicting greens/walks on non-permissive movements → fault flash** (typical trip ~350 ms; ignore < ~200 ms debounce; catch recurrent flicker). ([EDI MMU2-16LE §2.1](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-2 `[MON]` CRITICAL — Dual/multiple indications on one head (G+Y, G+R, Y+R…) → fault.** ([EDI MMU2-16LE §3.2](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-3 `[MON]` CRITICAL — Red-fail / dark approach (no indication on a head) → fault.** ([EDI MMU2-16LE §2.2](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-4 `[MON]` CRITICAL — Short/skipped yellow+red clearance between conflicting greens → fault.** The hardware backstop for FSM-1; a bug that shortens clearance is caught and flashed. ([EDI MMU2-16LE §2.5](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-5 `[MON]` CRITICAL — Watchdog/heartbeat timeout → fault.** External watchdog toggled ~every 100 ms; internal MPU transition every 5 ms (fault at 300 ms). A hung controller cannot hold live greens. Mirror as a software heartbeat: no fresh authenticated tick ⇒ safe state. ([EDI MMU2-16LE §3.3](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-6 `[MON]` CRITICAL — Supply/health faults (low +24 V, absent controller-voltage-monitor signal, Port-1/SDLC comms timeout) → fault flash.** ([EDI MMU2-16LE §2.3/§2.7](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-7 `[MON]` CRITICAL — Faults latch; the coordinator/arbiter may not clear its own fault.** Explicit external reset only. ([EDI MMU2-16LE §2.1](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **MON-8 `[MON]` CRITICAL — Positive, unambiguous grant indication.** A requester must never *assume* it holds the junction; give an explicit grant/deny (SSM/confirmation-light analog). Ambiguous/absent confirmation caused a real fire-engine/LRT collision. ([FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm); [ARC-IT SSM reply](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn))
- **MON-9 `[MON]` CRITICAL — Only one approach granted at a time, with an observable "granted-to" token** so a second responder from another leg knows it was *not* granted (Opticom steady-vs-flashing confirmation semantics). ([Galax FD: Opticom](https://galaxfire.com/equipment/opticom/))
- **MON-10 `[MON]` RECOMMENDED — No-stage-skip constraint.** Even adaptive priority (SCOOT) constrains recalls so stages are not skipped. ([Leeds UTMC01](https://www.its.leeds.ac.uk/projects/spruce/utmc1rev.html))

## 5. Security — every request authenticated, fresh, plausible, logged

- **SEC-1 `[SEC]` CRITICAL — Authenticate/integrity-protect every preempt request; reject unsigned/unverified before the arbiter sees it.** ARC-IT rates the emergency-preemption request flow **Integrity = HIGH, Authenticable = True**, warning unauthorized requests "could bring traffic to a standstill … citywide." ([ARC-IT security triple](https://www.arc-it.net/html/triples/s42d9f303.html); [CTI 4501 v01.01](https://www.ite.org/ITEORG/assets/File/Standards/CTI%204501v0101.pdf))
- **SEC-2 `[SEC]` CRITICAL — Bind authorization (who may preempt, and their class) to a certificate/registry, not a message field.** IEEE 1609.2 + SCMS issue certs carrying PSID/Service-Specific-Permissions; enforce expiry and revocation (CRL). Mirrors statutes that restrict preemption devices to enumerated authorized operators. ([SCMS fact sheet](https://www.engineering.virginia.edu/sites/default/files/Connected-Vehicle-PFS/Resources/CV%20PFS%20SCMS%20Fact%20Sheet%2003072022.pdf); [CT Gen. Stat. §14-299a](https://law.justia.com/codes/connecticut/title-14/chapter-249/section-14-299a/))
- **SEC-3 `[SEC]` CRITICAL — Freshness window + replay cache.** IEEE 1609.2 carries a generation time (+ optional expiry) and rejects byte-identical replays; accept only recently-generated, non-expired, non-replayed messages. Use the J2735 timeStamp/second/sequenceNumber. ([IEEE 1609.2a-2017](https://docbox.etsi.org/STF/Archive/STF538_TC_ITS/STFworkarea/libaries/IEEE_Std_1609_2a-2017.pdf); [ISO/SAE J2735 ASN.1](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn))
- **SEC-4 `[SEC]` CRITICAL — Byte-identical replay detection is necessary but NOT sufficient** — an attacker who re-signs with a fresh timestamp defeats it. Pair with plausibility (SEC-5). Experts: robust replay resistance "really need[s] either a timestamp or a three-way handshake (or preferably both)." ([Princeton CITP](https://blog.citp.princeton.edu/2003/10/27/remote-controls-traffic-lights/))
- **SEC-5 `[SEC]` CRITICAL — Plausibility-gate every request server-side** before it can drive a grant: position on a known approach, speed/heading/acceleration consistent with prior track, no impossible jumps, message-frequency sane. THEA CV-pilot misbehavior checks are directly transferable. ([THEA CV Pilot](https://rosap.ntl.bts.gov/view/dot/42690/dot_42690_DS1.pdf))
- **SEC-6 `[SEC]` CRITICAL — GPS is unauthenticated and spoofable (<$100 kit); don't grant on a single self-reported fix.** Cross-check position vs MAP geometry and prior track; detect meaconing (time jumps backwards). ([GPS spoofing survey (arXiv)](https://arxiv.org/pdf/1808.03515); [Infrastructure GPS-spoof detection (arXiv)](https://arxiv.org/pdf/2202.05463))
- **SEC-7 `[SEC]` CRITICAL — Rate-limit per source/certificate and bound queues to survive request flooding (DoS).** Signature verification alone does not stop inauthentic-SRM floods. ([ACM TCPS](https://dl.acm.org/doi/10.1145/3801748))
- **SEC-8 `[SEC]` RECOMMENDED — Immutable audit log of every request/grant/deny** with vehicle id, class, timestamp, junction, and reason (hash-chained). Commercial systems log the requesting vehicle and both successful and failed attempts; enables abuse detection/forensics and RBAC. ([Opticom Central Mgmt](https://www.itsinternational.com/its8/products/opticom-central-management-software); [Schneier: preemption logging](https://www.schneier.com/blog/archives/2023/02/a-device-to-turn-traffic-lights-green.html))
- **SEC-9 `[SEC]` CRITICAL — Fail-safe default beats obedience.** "The system has to recognize that defaulting to the old behavior is better than obeying an endless stream of commands, authorized or not." On loss of a fresh authenticated command/heartbeat, drop to the safe local state. ([Princeton CITP](https://blog.citp.princeton.edu/2003/10/27/remote-controls-traffic-lights/))
- **SEC-10 `[SEC]` RECOMMENDED — Emit a status reply with an explicit reject path (SSM).** Not every request is granted; the requester must be told granted/queued/rejected so it never assumes right-of-way. ([ISO/SAE J2735 SSM](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn))

## 6. Failure & degraded modes — the deployability tests

- **FAIL-1 `[FSM]``[CO]` CRITICAL — Central/comms loss → revert to local actuated/free operation;** never hold a coordinated or preempt state on stale input. The MMU remains the final backstop. ([Eltec: controller malfunctions](https://elteccorp.com/traffic-signal-controller-malfunctions-and-solutions/); [FHWA Ch.9](https://ops.fhwa.dot.gov/publications/fhwahop08024/chapter9.htm))
- **FAIL-2 `[CO]``[FSM]` CRITICAL — Ambulance signal/telemetry drops mid-corridor → the affected junction's hold times out (FSM-8) and the corridor reverts;** it must not keep blasting greens. ([ISO/SAE J2735 duration](https://forge.etsi.org/rep/ITS/WIRESHARK_ITS_PLUGINS/raw/master/itsis/ISO_TS_19091_DSRC.asn))
- **FAIL-3 `[FSM]` CRITICAL — Stuck/absent detector or preempt call → gate it.** A locked call maxes green; an absent call needs a defined fallback (max recall raises delay 50%+). A call that never clears or is implausibly long must be flagged and dropped. ([FHWA Traffic Detector Handbook Ch.6](https://www.fhwa.dot.gov/publications/research/operations/its/06139/chapt6.cfm))
- **FAIL-4 `[MON]` CRITICAL — Controller hung / power loss → flash-red default** (watchdog + supply monitors, MON-5/6). ([EDI MMU2-16LE](https://www.editraffic.com/wp-content/uploads/2020/11/MMU2-16LE-Operation-Manual-888-2116-001-1.pdf))
- **FAIL-5 `[ARB]``[SEC]` CRITICAL — Split-brain / duplicate controllers → single-writer fencing.** Each grant carries a monotonically increasing writer epoch; an edge ignores any command with an epoch below the last it accepted. (Backend hardening pattern; complements the fail-safe supervised interconnect MUTCD requires for rail.) ([MUTCD 11th Ed. Part 8D.09 fail-safe interconnect](https://mutcd.fhwa.dot.gov/pdfs/11th_Edition/part8.pdf))
- **FAIL-6 `[FSM]``[CO]` CRITICAL (near rail) — Preempt trap:** insufficient track-clearance green can strand a vehicle on the tracks; size right-of-way-transfer + track-clearance + queue-clearance + a **4 s** separation buffer, lock out toward-track movements in dwell, and interconnect with rail equipment. ([NCHRP Synthesis 507](https://transops.s3.amazonaws.com/uploaded_files/NCHRP%20Synthesis%20507%20Traffic%20Signal%20Preemption%20at%20Intersections%20Near%20Highway%E2%80%93Rail%20Grade%20Crossings.pdf); [FHWA Grade Crossing Handbook App.I](https://toolkits.ite.org/gradecrossing/appeni.htm))
- **FAIL-7 `[SEC]` CRITICAL — Spoofed/replayed request** (legacy IR MIRT spoofed with a Flipper Zero / Arduino + IR LED, including a vehicle id) → defeated by SEC-1..6; and even a spoofed grant still runs the normal green→amber→red sequence, so clearance rules (FSM-1) are the ultimate net. ([Hackaday: spoofing preemption](https://hackaday.com/2026/03/08/spoofing-an-emergency-traffic-preemption-signal/); [Schneier](https://www.schneier.com/blog/archives/2023/02/a-device-to-turn-traffic-lights-green.html))
- **FAIL-8 `[CO]` RECOMMENDED — Cloud/cellular release latency** (observed 10 s+) and area-wide cellular failure during emergencies → don't depend on a "clear" message to release; use the independent max-hold timeout (FSM-8). ([Wikipedia: preemption — cloud caveat](https://en.wikipedia.org/wiki/Traffic_signal_preemption))

## 7. Invariants — the always-true test oracle

Assert these continuously in the C1–C12 (and fuzz) tests; any violation is a bug:

1. **No conflicting greens** at any junction, ever — `not (nsGreen and ewGreen)` and no dual indication. (MON-1/2)
2. **Clearance always served** — every green→red passes through the full yellow + all-red; no yellow→green. (FSM-1/2, MON-4)
3. **Min-green respected** before any switch. (FSM-4)
4. **Pedestrian clearance never below the calculated floor** except under true preemption geometry. (FSM-5)
5. **Every hold is time-bounded** and reverts on duration/lease expiry. (FSM-8, FAIL-2)
6. **Exactly one preempt served** per junction; priority order rail > EV > transit honored; higher overrides lower. (ARB-1/4)
7. **No unauthenticated or implausible request ever produces a grant.** (SEC-1/5)
8. **Safety monitor latches on fault** and is not clearable by the corridor logic. (MON-7)
9. **On comms/heartbeat loss the system reaches a safe state** (local actuated / flash), never a stuck green. (FAIL-1/4, SEC-9)

## 8. What's new here vs. the earlier C1–C38 list

The earlier C1–C12/C13–C38 cases were behavioral scenarios. This catalog grounds them in standards and adds the *deployability* requirements that make the backend bullet-proof: the independent latching conflict monitor and its full fault set (MON-1..7), the inviolable clearance/min-green/ped-clearance constraints (FSM-1..6), the fixed rail>EV>transit arbitration with controller-retains-authority (ARB-1..5), the green-wave offset math and managed recovery (CO-1..7), and the entire security layer — authentication, freshness, replay+plausibility, DoS rate-limiting, and fail-safe-over-obedience (SEC-1..10). The failure modes (FAIL-1..8) are the tests that decide whether it's a demo or a system.
